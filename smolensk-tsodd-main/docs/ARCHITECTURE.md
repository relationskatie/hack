# Архитектура проекта ЦОДД Смоленской области

## Обзор архитектуры

Проект построен на современной архитектуре Next.js 15 с использованием App Router и следует принципам **Feature-based архитектуры** для обеспечения масштабируемости и поддерживаемости кода.

## 🏗 Структурная архитектура

### 1. App Router (Next.js 15)
```
src/app/
├── layout.tsx              # Корневой layout
├── layout-client.tsx       # Клиентский layout с провайдерами
├── page.tsx               # Главная страница
├── globals.css            # Глобальные стили
├── not-found.tsx          # 404 страница
└── [feature]/             # Страницы по функциональности
    ├── page.tsx           # Основная страница
    ├── [id]/              # Динамические маршруты
    └── layout.tsx         # Layout для группы страниц
```

### 2. Feature-based модули
```
src/features/
├── [feature-name]/
│   ├── components/        # Компоненты модуля
│   ├── services/          # API сервисы
│   ├── types/            # TypeScript типы
│   ├── hooks/            # Кастомные хуки
│   └── index.ts          # Публичный API модуля
```

### 3. Shared слой
```
src/shared/
├── api/                  # HTTP клиент
├── components/           # Переиспользуемые компоненты
├── constants/            # Константы и конфигурация
├── contexts/             # React Context
├── hooks/                # Общие хуки
├── types/                # Общие типы
└── utils/                # Утилиты
```

## 🔄 Потоки данных

### 1. Аутентификация
```
Login → AuthContext → ProtectedRoute → API calls with token
```

### 2. API взаимодействие
```
Component → Feature Service → HTTP Client → Backend API
```

### 3. Управление состоянием
```
Local State (useState) → Context API → Zustand (при необходимости)
```

## 🎯 Архитектурные принципы

### 1. Разделение ответственности
- **App Router** - маршрутизация и SSR
- **Features** - бизнес-логика по доменам
- **Shared** - переиспользуемые компоненты
- **Types** - типизация данных

### 2. Инверсия зависимостей
- Компоненты зависят от абстракций (сервисы)
- Сервисы инжектируются через Context или props
- API клиент абстрагирован от конкретных эндпоинтов

### 3. Единообразие интерфейсов
- Все API сервисы следуют единому паттерну
- Компоненты имеют консистентные props
- Типы данных стандартизированы

## 🧩 Паттерны проектирования

### 1. Feature-based модули
```typescript
// Каждый feature экспортирует только необходимый API
export { NewsList } from './components/NewsList';
export { useNews } from './hooks/useNews';
export type { News } from './types/news.types';
```

### 2. Композиция компонентов
```typescript
// Компоненты собираются из более мелких частей
<NewsSection>
  <NewsHeader />
  <NewsList />
  <NewsPagination />
</NewsSection>
```

### 3. HOC для защиты маршрутов
```typescript
// ProtectedRoute оборачивает защищенные компоненты
<ProtectedRoute requiredRole="admin">
  <AdminPanel />
</ProtectedRoute>
```
